# KaizPatchX 1.10.4: 自由端点でのRailMap往復と位置飛び

2026-10-10 ローカルCodex。提出ログ: logs/fml-client-latest.log。実行版はログのRTM/NGTLib宣言と使用JARから **KaizPatchX 1.10.4** と確認。SRBXの型生成基準v1.10.3と混同しない。

## 結論

AEと共通する背景は、ブロック内部の精密接続点に対して道床が単一コアの所有情報しか持たないこと。一方、KaizPatch 1.10.4には既に端点越えの接続先探索があり、AEとまったく同じ処理ではない。

今回Kaizでは、新しいRailMapへ切り替えた次tickに旧RailMapへ戻る **切替の往復** が確認された。端点探索と道床探索の競合という説明が、ログと実装の探索順に整合する。逆方向にも速度値より大きい1 tick変位がある。動作上はRailTransitionResolverとブロック探索fallbackの相互作用に整合する。ただし、[Issue #534の制作者見解](https://github.com/Kai-Z-JP/KaizPatchX/issues/534#issuecomment-6086321090)では、曲線端点をブロック端に置く保証はスクリプト側の責務で、今回の配置は遷移できない方が正しいとされている。**KaizPatchの修正義務ではなく、SRBXが生成条件を満たしていない状態として扱う。**

SRBXが生成した自由端点接続で再現。初回は短い自動分割セクションがあったが、位置変更後は5.85585 mの区間でも同じ往復が発生し、極短区間は必要条件ではない。当初はサポート範囲未確認だったが、上記見解を受けてSRBX側の対応設計が必要。今回SRBX/Mod/車両コードの変更は行わない。道床所有先を再上書きしても一方向側を変えるだけで、両方向の解決にはならない。標準マーカー＋offset等によるSRBX非経由の実機対照は未実施。ログと実装の原因説明は維持し、責務判断はIssue回答を優先する。AEの想定仕様にこの回答を適用しない。

SRBXでの選択肢は、生成・分割・移動・カント分割の接続端点を標準の境界条件へ合わせるか、任意精密端点を支える独自の遷移補正を追加すること。[スクリプト/補助Modの実現性検討](free-endpoint-transition-patch-feasibility.md)を参照。

## ログの事実

必要箇所のみ [kaizpatch-104-transition-oscillation-20261010.log](../logs/kaizpatch-104-transition-oscillation-20261010.log) に抜粋。生ログ・PC情報・ローカルパスは追加しない。

- 精密接続点P = **(-709.85950,4.06250,31.85950)**。床ブロック **(-710,4,31)** は旧論理レールのコア(-705,4,26)を所有先として保持。
- 旧物理RailMapは(-704.00000,4.06250,25.99989)→P、長さ8.28660 m。
- 新物理RailMapはP→(-710.00001,4.06250,32.00000)、長さ **0.19871 m**、コア(-711,4,32)。この後に約14.14220 mの次セクション(-712,4,33)がある。
- 新短区間の生成ログはadded=0, retained=0。その内部は旧道床の同じ床セルにあり、別コアを持つ接続先短区間があることを端点探索で解決する必要がある。

410～496の**87 tick全て**に観測があり、先頭コアが毎tick交互に切り替わる。旧コアへ戻ったときの車体位置は(-708.97556,5.25000,30.97555)、旧台車バッファはPの上方。AEの完全静止とは異なり、毎tick前後に動くため現行possible-stall条件（微小移動40 tick継続）には該当しない。

この区間の通過速度はAEで計算した14.31 km/hと同じ値ではない。初回は約7.57 km/hで次区間へ抜けているが、後述の位置変更試験では次区間に到達せず、接続先を所有する床セルに進んだ時点で往復が止まる。短区間を飛び越すことは通過の必須条件ではなく、予測点の床所有先も関係する。全条件に使える速度閾値とは扱わない。

### 逆向き: 車両id=505263

- tick347→348: 速度0.014448→0.014248 m/tick（約1 km/h）と減少する一方、車体が **約0.188196 m** 移動。先頭台車が短区間(-711,4,32)から旧区間(-705,4,26)へ切替、旧終端index=2983へ戻る。
- tick501→502: 速度は **0.015416 m/tickで同じ**、車体変位 **約0.106285 m**。後台車が同じ接続を切替。
- 台車posとbufのYは5.25、RailMap端点Yは4.0625。一定の差1.1875 mが記録されているが、AEの台車とそのままYを比較して段差の原因とは断定しない。今回問題の変位は水平X/Zに現れている。

## 1.10.4の実行コードとの対応

ログに記載された実使用JARを調査用キャッシュへコピーし、javapでEntityBogieとjp.kaiz.kaizpatch.rtm.rail.util.RailTransitionResolverを確認。インストール済みModとGradle依存は変更していない。

1. EntityBogie.getRailは最初に **findCrossedConnectedCore** を呼び、越えた端点の接続コアが見つかればそれを採用する。
2. 越えた端点がない場合、予測X/Zの床セルで **getRailFromCoordinates** を実行する。床が存在する場合はそのコアを取得し、**keepCurrentSectionCore** の結果を採用する。
3. keepCurrentSectionCoreには現在コア/候補の同一性・isSameLogicalRailが渡される。今回往復する2コアは **別の論理グループ**。同一論理レール内のコア保持では保護されない。
4. resetRailObjは別グループなら **canConnect** を検査する。今回実際に何度も切替が成立しているため、「接続できない判定で進めない」ケースとは異なる。
5. 切替時には **findConnectedEntryIndex** で新しいmapの入口indexを設定し、updateBogiePosがそのmapへ台車位置を投影する。候補が旧mapの場合にはその終端側へ戻る。

短区間に入った直後の予測点はまだ同じ旧床セル内なので、次tickの床探索が旧コアを候補として返す。端点を越えていない現在の短区間を保持せず、接続関係のある旧コアへ戻ることがログの毎tick往復と整合する。逆方向でも短区間をまだ通過中に旧コアが床候補として採用され、実接続点より早く旧端へ投影される。

## 位置変更後の追加検証: 極短区間なしでも再現

同日の差替ログでも実行版は1.10.4。必要箇所は[追加ログ抜粋](../logs/kaizpatch-long-section-transition-20261010.log)。

- 接続点P2 = **(-713.85950,4.06250,27.85950)**。床セル(-714,4,27)の所有コアは旧(-705,4,18)。
- 旧物理区間は長さ13.94352 m、接続先区間はP2→(-718.00026,4.06250,32)、**長さ5.85585 m**、コア(-715,4,28)。前回の0.19871 m区間はこの接続に存在しない。接続先区間にもadded=22の道床生成を確認。
- id485199のtick441～531は**全91tickで先頭台車の新旧コアが交互に切替**。例: tick441は新index9/2108、442は旧5019/5019、443は新10/2108、444は旧5019/5019。毎回旧終端へ戻り、別論理グループ間の往復という初回と同じ挙動。
- tick531（速度0.100888 m/tick）は新index36/2108だが、床所有先は旧。tick532（0.102424 m/tick、約7.37 km/h）は**同じ新mapのindex72/2108**へ進み、床セル(-715,4,28)の所有先が新コアへ変わる。次の区間を越えずに往復が止まり、初期区間長より床セルの所有先が重要という説明を補強する。
- 逆方向id572178は先頭tick365、後台車tick448で旧終端へ切替。先頭の直前観測tick362は新map index96/2108。車体の362→365は約0.26667 m/3tick、445→448は約0.17918 m/3tickで、速度は約0.028 m/tick。ただし途中2tickの記録がないため、初回と同じ精度の単tick位置飛び量は算出できない。

**極短レール単独の問題という仮説は、今回の接続について否定された。** ブロック内部の精密接続点と、道床所有コアによる再選択の競合は引き続き説明として整合する。全自動分割区間・通常レールで同条件かは未検証。

## 初回の相談文（Issue回答前の記録）

KaizPatchX 1.10.4で、自由端点接続を低速走行すると、台車が新旧の物理コアを毎tick往復する例があります。初回の約0.19871 m区間では逆向きに速度値が減少/一定でも切替時に位置が約0.19 m/0.11 m飛びます。位置変更後の5.85585 m区間でも新旧コアの往復が91tick連続で再現したため、極短区間に限定されません。

新旧RailMapの接続点は(-709.8595,4.0625,31.8595)。その床セル(-710,4,31)は旧コア(-705,4,26)を指します。接続先の短区間は同点から(-710.00001,4.0625,32)までで、コアは(-711,4,32)。旧/新は別の論理グループ、カント0・水平、検証車両は台車間隔2.5 mの単車です。

追加検証では接続点(-713.8595,4.0625,27.8595)、旧コア(-705,4,18)、新コア(-715,4,28)、新区間長5.85585 mです。同じ新mapのindex36→72で床所有先が新コアへ変わると往復が止まり、次の区間まで走り抜ける必要はありません。

findCrossedConnectedCoreで接続先区間へ入った後、次tickのgetRailFromCoordinatesが旧床の所有コアを返し、keepCurrentSectionCoreでは別論理グループなので保持されず、findConnectedEntryIndexで旧終端へ戻っているように見えます。接続先へ入った後は、現在のRailMapを実際に出るまで床候補による旧レールへの再選択を避けるなど、1.10.4の遷移補完側で対処できるか相談したいです。

この自由端点接続をサポート外とする場合は、必要な座標・最小長さ・ブロック所有配置の制約を教えていただきたいです。重複線路・分岐・同論理グループの内部遷移もあるため、対応方針は制作者の判断に委ねます。
