# AppleExtended: 自由端点接続の低速停止・遷移時位置補正

調査: 2026-10-10 ローカルCodex。対象: AppleExtended v2.5.3。提出ログ: logs/latest.log、必要箇所の抜粋: [appleextended-directional-transition-20261010.log](../logs/appleextended-directional-transition-20261010.log)。

## 結論と対応範囲

今回の症状は、SRBXが生成したブロック内部の精密接続点と、AEのブロック所有先による台車RailMap探索の不整合で説明できる。道床上書きが原因とは確認できず、所有先を片方に付け替えるだけでは双方向走行を保証できない。

任意の精密端点を保持して双方向の低速遷移を実現するには、AE側の端点を考慮した遷移処理が必要。AE制作者には「自由端点接続の走行制約・対応可否」として相談する。setPositionが任意座標の指定を許しても任意接続の走行を保証するとは限らないため、AEの契約違反と断定しない。

SRBX側にもこの制約を考慮する責任はある。回避策は接続点をブロック境界に合わせること、または同一セル内接続を制限すること。ただし既設レール両側の精密線形を変える/自由端点機能を制限する仕様変更となる。今回、SRBXの特定敷設処理だけを直せば精密接続が成立する不具合とは確認できなかったため、自動座標変更・道床所有先再上書き・車両速度/RailMapの強制変更は実施しない。

## 実ログで確認した事実

接続点は **(1405.85950, 4.06250, -1600.85950)**。所属ブロックは **(1405, 4, -1601)** であり、そのブロックは接続元コア自身。

速度値の増加を伴わない1 tickの変位超過があるため、Bの「加速感」はRailMapへの位置投影による飛びとして説明できる。phase=before-movementのため、この台車情報は直前の編成移動結果であり、当tick速度更新との時間差がある。それでもBの390/391は速度値が同じで、通常の加速だけでは説明できない。

## 一次ソースとの対応

ローカルの公式AE v2.5.3 JARをjavapで確認。Mod/rtm-tsは変更していない。

1. EntityBogie.updateBogiePosは位置と速度、movingYawから予測X/Zを作り、resetRailObjを先に呼ぶ。
2. EntityBogie.getRailはTileEntityLargeRailBase.getRailFromCoordinatesへ渡す。後者は予測X/Zをfloorした1列の道床を検索し、その所有コアを取得する。精密接続端点を越えたかどうかに基づく別レール探索はない。
3. resetRailObjは所有コアが変わった場合にcurrentRailMapを置換し、prevPosIndex=-1へ戻す。
4. updateBogiePosは選ばれたmap内の最近傍サンプルへ投影する。mapの範囲外は始点/終点へ戻り、別mapへ進む距離を保存して渡す処理はない。

Aでは先頭台車が精密始点に達しても、約0.028 mの予測移動では次のブロックに到達せず、旧mapが選ばれ続けてindex=0へ戻る。逆方向Bでは次ブロックの所有コアに入る時点が精密接続点より前なので、切替先mapの始点へ早く投影される。

直線がX増加/Z減少の45度方向とすると、接続点から次のセル境界までの距離は (1406-1405.85950)×sqrt(2) ≈ **0.198697 m**。20 TPS換算で約14.31 km/h。Aがspeed=0.201352で通過した記録と整合する。この閾値計算はログの線形に基づく推定であり、一般の曲線・勾配にそのまま適用する値ではない。

## 制作者への再現条件・相談文

AppleExtended v2.5.3で、直線2本をブロック内部の同じ精密座標へ接続すると、一方向の低速走行がRailMap端で停止し、逆方向では速度値一定でも台車のRailMap切替時に位置が飛ぶ例があります。

今回の接続点は(1405.85950,4.06250,-1600.85950)、道床所有コアは(1405,4,-1601)。一方の物理RailMapはこの点を始点として(1392.00000,4.06250,-1587.00015)へ、他方は(1408.00000,4.06250,-1603.00002)からこの点を終点として接続しています。カントは0、水平です。SRBX_TrainDebug単車、台車間隔2.5 m、約2 km/hで確認しました。

道床のブロック所有先による探索と、RailMapへの端部投影によって、精密接続点とブロック境界の差が移動不能/位置補正に現れるように見えます。RailPosition.setPositionで自由端点を使う場合、この接続はサポート外でしょうか。サポート可能であれば、端点を越えた際に幾何学的に接続するRailMapを探索し、超過移動量を引き継ぐ遷移へ対応できるか相談したいです。

探索変更時には、分岐の有効経路、重なった別線路、自動分割グループ、方向・高さ・カントの判定も必要と思われます。実装方針は制作者の判断に委ねます。

## 残る比較確認

- 今回の実機ログはAEのみ。KaizPatchにも同系統のブロック所有先探索があるが、このログだけでKaizの全ケースを実証したとは扱わない。
- SRBXを介さない同じ精密端点/所有状態でも起こる構造と判断しているが、標準マーカー＋端点offsetを使う実機対照試験は未実施。境界に一致する接続と、ブロック内部の接続を同じ車両で比較して制作者に提示する。
- 初回レール敷設の所有先変更履歴は今回ログに無いため、上書きが過去に無かったことまでは断定しない。ただし今回の保存状態だけで両方向の挙動を説明できる。
- 現行パックのデバッグ車両は観測用として引き続き使用可能。生成・走行のコード変更や新しいZIP作成は今回行わない。
