# 自由端点接続: SRBXからの遷移パッチ実現性

2026-10-10 ローカルCodex。対象: KaizPatchX 1.10.4 / AE 2.5.3。実装・実機パッチ試験は未実施。

## 結論

**SRBXの既存描画パッチと同じ方法では、台車のJava探索処理を直接差し替えられない。** 任意精密端点を維持して一般車両の走行を補正するには、起動時に探索処理へ介入する補助Mod/coremodが有力。SRBXパックだけでも大規模な車両処理の置換を検討する余地はあるが、現在の調査では全車両に安全に適用できる仕組みは成立していない。

[KaizPatch Issue #534回答](https://github.com/Kai-Z-JP/KaizPatchX/issues/534#issuecomment-6086321090)では端点のブロック端配置はスクリプト側の責務。補助パッチは標準仕様の修正を求めるものではなく、SRBXが任意精密端点を拡張機能として支えるための独自実装となる。AEへの適用はその仕様・実装を別途確認する。

## 介入箇所の確認

- 現行SRBX描画パッチはModelSetRailClientのrendererが持つScriptEngineへevalし、renderRailDynamic2等のJavaScript関数を差し替える。車両Javaクラスのバイトコードを書き換える機構ではない。
- KaizのEntityBogie.updateBogiePosは予測点を計算し、private resetRailObj→private getRailへ進む。getRailはRailTransitionResolverのstatic findCrossedConnectedCoreと道床探索を呼ぶ。resolverクラスはfinal。JavaScriptの関数代入やJava.extendで、既存オブジェクトのprivateメソッド・static呼出先を上書きすることはできない。
- 公開updateBogiePosを持つ別の台車サブクラスやBogieControllerの置換は概念上別案だが、既存台車のクラスは変えられず、エンティティ生成・同期・保存/復元・編成処理まで含む実装が必要。KaizのcontrollerにはsetBogieがあるが、参照の差替えだけでワールド/クライアントの台車が整合する保証はない。
- SRBXの走行診断は専用モデルのserver onUpdateから移動前の内部状態を読み取る。全モデル/全台車のネイティブ探索直前へ介入する共通フックは現在のSRBXにない。reflectionによるフィールド読取りは確認済みだが、メソッド差替えの根拠にはならない。

## 案の比較

| 案 | 実現性・課題 | 判断 |
| --- | --- | --- |
| 台車のcore/map/indexを毎tick書換え | 移動前のnative床探索で再選択され得る。移動後に直すと位置飛び・編成距離・同期の補正まで必要 | 汎用対処として採用しない |
| 通過時に道床の所有先を一時変更 | 全車両が共有する床情報を変更し、逆方向車両/複数列車/Undoと競合 | 採用しない |
| 車両スクリプト注入・controller/台車の置換 | 専用車両での試作余地はあるが、既存モデルのcallback、保存された台車、編成、クライアント同期への対応が広い | パック単独案は未成立 |
| 補助Mod/coremodでJava探索へhook | 元ModのJAR・rtm-tsを変更せず、起動時のクラス変換で介入する構成が候補。追加JARの配布/導入が必要 | 任意精密端点を維持する有力案 |
| 生成側で標準端点条件を満たす | 現行パック内で実装できるが、座標/線形/分割位置が変わり自由端点の仕様が制限される | 追加Modなしの候補 |

coremodは既存JARを直接改造しなくても、実行時のKaiz/AEの挙動を変更する。現行リソースパックと同じ配布形態ではない。既にロードされたクラスをpackのbootstrapから再定義するには別のInstrumentation等の仕組みが必要で、現在のSRBXにはない。

## 補助Modの最小設計候補

1. **台車ごとに**現在map・現在位置・予測点・進行方向を使って、現在区間を実際に出たかを判定する。床所有先だけで現在mapを捨てない。
2. 現在区間内なら、接続端点付近の床が隣接する旧コアを返しても現在mapを優先する。ただしmapへの近接、進行方向、コアの存続、端点の接続関係を検証し、単にindexが端でないという条件にはしない。
3. 区間を出たら、精密端点でつながる次mapを選び、残りの移動距離を引き継ぐ。極短区間を複数越えるケースには探索回数上限を置く。
4. Kaizは既存findCrossedConnectedCoreを活用し、fallbackによる旧mapの再選択を抑えるhookを検討。AEは端点越えの接続先解決自体を追加する必要がある。両ターゲットで同じクラス変換を使わない。
5. 分岐/交差/重複線路では接続関係と経路選択を尊重し、不明な候補へ強制遷移しない。状態不整合や未対応の実装版なら補正を無効化して一度だけ診断する。
6. 当初は確認済みバージョンと明示的な対象範囲に限定し、通常レール・他モデルへの影響を比較する。SRBX生成を識別する永続情報は現在未設計のため、対象限定方法も決める必要がある。

KaizのkeepCurrentSectionCoreで無条件に現在コアを返すだけの変更は不十分。同論理グループ外への正当な遷移や逆向きの端点越えまで抑えないよう、幾何条件と接続関係を組み合わせる。

## 検証と未確認事項

確認済み: 現行描画パッチ/診断スクリプトの介入範囲、実使用Kaiz JARのprivate/static/final構造、台車更新→予測→探索の順序、旧床探索との競合を示す実機ログ。今回ソース変更・バイトコード変換・ワールド書換えはしていない。

未確認: 補助Modのloader登録・変換実装、SRBXパック単独での車両置換、既存/保存台車の互換性、Java/Forge実行環境ごとの可否。試作時には双方向の微速、停止/後退、5.86 mと0.20 m区間、勾配/カント、分岐/交差、複数列車、編成長、チャンク再読込、敷設/移動/Undo後を実機比較する。

現段階では実現性検討まで。追加JARを許容するか、境界配置による自由端点の制限を選ぶか、配布形態と操作仕様の判断が必要。既存ワールドの自動端点移動は行わない。
