# RailPosition自由化の調査と試験実装

## 概要

KaizPatchX v1.10.2で追加された `RailPosition#setPosition(x, y, z)` は、レール曲線の端点を従来のブロック面中央に限定せず、ワールド座標で直接指定するAPIです。SuperRailBuilderXでは、この挙動を確認するための `SuperRailBuilderX_RailPositionTest` を追加しています。

公式説明: [KaizPatchX v1.10.2](https://github.com/Kai-Z-JP/KaizPatchX/releases/tag/v1.10.2)

## 内部で何が変わるか

RailPositionには従来からブロック座標、向き、高さなどがあり、それらから標準の端点座標が計算されます。自由化では標準座標との差分が `offsetX / offsetY / offsetZ` として保持され、`setPosition` がその差分を計算して端点を再初期化します。オフセットはNBTにも保存されます。

重要なのは、次の2種類の座標が別の役割を持つ点です。

| 座標                       | 主な役割                                           |
| -------------------------- | -------------------------------------------------- |
| `blockX / blockY / blockZ` | RailPositionを所有するブロック、探索・保存上の基準 |
| `posX / posY / posZ`       | 実際に曲線の端点として使われる精密なワールド座標   |

したがって、端点を動かしても所有ブロックが自動的に移るわけではありません。またRailPosition同士の同一性判定にはブロック座標が使われる箇所があり、精密座標だけを見ればよいとは限りません。

## 接続に関する制約

APIはブロック端から外れた座標も受け付けます。しかし、公式説明のとおり、列車が別レールへ正常に乗り移れる位置であることはスクリプト側で保証する必要があります。見た目の曲線が接していても、所有ブロック、RailPositionの向き、隣接判定との組み合わせ次第で接続として扱われない可能性があります。

試験ツールは理解のために任意位置へ移せるようにしています。同じ精密座標（許容差1 mm）に複数レールの端点がある場合は接続点としてまとめて選択し、同じ移動先へ更新します。サーバー側でも全端点が同じ元座標にあることと各レールの状態を事前検証してから適用します。実用ツールへ発展させる際は、接続相手の端点へのスナップ、ブロック境界への制限、接続可否のより厳密な事前検証を追加する想定です。

## KaizPatchXの自動分割レール

KaizPatchX 1.10.3の自動分割では、論理レールが跨ぐチャンク境界に応じて複数の `TileEntityLargeRailSectionCore` が生成されます。コア数は固定ではなく、曲線とチャンクの位置関係によって変わります。

始点側・中間・終点側のコアはすべて同じクラスで、配置時のブロックメタデータも共通です。そのため、端部をクラスやメタデータだけで区別することはできません。各コアには次の論理レール情報が保存されています。

- 同じ論理レールを識別するグループUUID
- グループを構成する全コアの座標リスト
- 論理レール全体の始点・終点となる2個のRailPosition
- 各コアが担当する曲線範囲の開始比率・終了比率

各コアの `getLogicalRailPositions()` は同じ論理端点2個のコピーを返します。候補探索では物理コア座標ではなくグループUUIDで重複を除き、この論理端点と視線位置の距離から始点・終点を選択します。

論理端点を変更する場合、1個のセクションコアだけを更新してもグループ全体へ反映されません。試験実装では、全グループコアがロード済みで列車が在線していないことを確認し、元の論理端点を退避してからKaizPatchXの `breakLogicalRail()` で論理レール全体を撤去します。変更後の曲線は `RailChunkSectioner.split()` で再分割し、各セクションを再生成します。移動前後でセクションコア数が増減する場合にも対応し、再生成に失敗した場合は退避した端点から元のレールを復元します。

自動分割レールでは、変更後の曲線から新しいセクションコアのブロック座標も選び直されます。この物理コアは空気・マーカー以外のブロックや別レールのコアと同じ座標には配置できません。そのため、曲線部分の道床が重なり可能でも、再分割後のコア候補が衝突すると標準再構築は失敗します。道床の事前検証を通過した後に `section_rebuild_failed` となる場合に備え、試験実装は `planned section cores` として候補座標・既存ブロックを再構築前にログへ記録します。

実機ログでは、セクションコア候補が他レールの通常道床 `LRBase` 上にある再構築は成功しました。KaizPatchX標準処理はこの道床を新しいセクションコアへ置き換えられます。一方、失敗例はいずれも他レールの物理コア `LRCore` との衝突でした。ここでは「新しいセクションコア自身の配置先が他コアと一致する場合」と「セクションの曲線途中が他コアのブロックを横切る場合」を区別する必要があります。

前者は1ブロックに2個のTileEntityを共存できないため、他レールを壊さずには配置できません。試験実装は `planned section core conflict` / `section_core_conflict(N)` として移動を中止します。後者は既存コアを保持し、交差座標への道床設置だけを省略する試験的なセクション再構築を行います。

2026-09-01の追加試験では、すべての複数セクション再生成について、道床ブロックを空気位置だけへ加算配置する方式に変更しました。既存の通常道床・レールコア・通常ブロックは曲線途中では保持します。ただし、新しいセクションコア予定位置に通常道床がある場合だけは、その1ブロックをセクションコアへ破壊的に置換します。置換数は `replacedRoadbedsWithCores` へ記録します。再生成失敗時は作成途中のコアを除去し、置換前道床の所有コア座標を復元してから元レールを再生成します。

撤去・復元を伴う試験を繰り返したワールドでは、論理情報が初期化されていないセクションコアが一時的または残骸として探索範囲に入ることがあります。`getLogicalRailPositions()` が有効な配列を返さないコアは論理端点として扱えないため、候補探索では `sectioned_uninitialized` として無視します。

## 試験ツールの操作

1. ツールを使用し、視線の衝突位置から半径約1ブロック以内にある通常レールまたは自動分割レールの論理端点を探します。
2. 表示された点の近くで右クリックし、最も近い端点を選びます。同じ座標を共有する端点が複数あれば、接続している端点をまとめて選択します。
3. 視線先に0.01 m単位で丸めた移動先プレビューが表示されます。
4. 右クリックで移動先を確定します。
5. Enterでサーバーへ適用を要求します。
6. 左クリックは、移動先確定から移動先選択へ、端点選択から未選択へと1段階ずつ戻します。

クライアントは探索、入力、プレビューだけを担当します。サーバーはRailPositionの元座標が選択時から変化していないか、複数対象が同じ接続点に属するか、全対象が移動可能かを再検証し、成功時に `setPosition`、RailMap再生成、保存・同期処理を行います。自動分割レールを含む再構築で適用途中に予期しない失敗が起きた場合は、`partial_target_...` を返してログへ適用済み件数を残します。

## 道床TileEntityと走行判定

列車はRailMapの曲線だけで走り続けるのではなく、各走行位置の下にある `TileEntityLargeRailBase` から所有レールコアを取得します。そのため、精密端点とRailMapだけを移動して道床範囲を更新しない場合、見た目上はレールに沿っていても新しい曲線が旧道床範囲を出た場所で `Rail not found` になります。

通常レールの試験実装では、変更後RailMapから必要な道床座標を再計算し、空気位置に不足する道床TileEntityだけを追加します。既存ブロックと移動前道床は削除せず、既存レールの道床も上書きしません。自動分割レールの試験再構築も同じ空気位置限定の道床配置を使い、セクションコア予定位置だけを上記の規則で置換します。

RTMの道床TileEntityは所有レールコア座標を1個だけ保持します。そのため、同じブロック座標に複数レールの道床所有情報を共存させることはできません。RTM標準の配置判定に合わせ、他レールの非コア道床との重なりは許可します。通常レールの加算更新は既存道床を残しますが、自動分割レールの標準再構築では後から配置したレールの所有情報へ上書きされる場合があります。

通常レールでは、見かけ上の重ね・交差を妨げないため、変更後の道床範囲にレールコアや非レールブロックがあっても端点とRailMapの移動自体は許可します。該当座標には道床を追加せず、既存ブロックを残して `normal roadbed obstacles retained` を記録します。その座標で移動後レールを所有する道床を確保できないため、交差部を列車が問題なく通過できる保証はありません。自動分割レールも曲線途中は同様に保持しますが、セクションコア予定位置に他レールコアや通常ブロックがある場合は安全のため停止します。

曲線端の隣接ブロックは標準の道床生成対象から除外されます。KaizPatchXは端点通過時に精密端点と接続可能な別コアを前方探索するため、接続端点が一致していれば移動前道床を接続部へ残すこと自体は必須ではありません。ただし、複数レールが同一ブロックを長く共有する構成は上記の所有情報制約があり、別途設計が必要です。

## 現在の安全制限

- KaizPatchXターゲット専用です。他ターゲットでは候補を表示せず、適用もしません。
- KaizPatchX 1.10.3環境では、通常のレールマーカーで設置したレールが自動分割セクションになる場合があります。論理端点の選択・再構築とセクション数の増減は実機で動作確認済みです。SuperRailBuilder3が生成した非セクションレールも選択・移動できることを確認済みです。
- `RailPosition#setPosition` 自体は分岐器のRailPositionにも精密座標を設定できます。ただし分岐器は3個以上のRailPositionと複数の `RailMapSwitch` を持ち、`TileEntityLargeRailSwitchCore` は生成済みの分岐オブジェクトをキャッシュします。通常レール用の単一端点更新ではこの分岐オブジェクトが再生成されず、保存されたRailPositionと描画・走行用RailMapが不一致になります。全端点・道床・分岐オブジェクトを一体で再構築する専用対応を実装するまでは選択対象外にします。
- 自動分割レールの再構築中はレールブロックを一度撤去して再配置します。配置失敗時の復元処理はありますが、初回検証はバックアップしたテストワールドで行ってください。
- 他レールコアを曲線途中で保持する自動分割レールの交差再構築は試験段階です。両方のレールについて交差部を双方向に走行し、`Rail not found` や意図しない転線が起きないことを確認してください。
- 自動分割レール移動時に発生していた `getWorldObj` の実行時エラーは、KaizPatchXの実行名へ変換される基本コア型のcompatヘルパーを経由することで修正しました。要求処理は例外時にも必ず消費し、同じエラーを毎tick再実行しません。
- 通常レールの移動では新しい曲線に不足する道床だけを追加し、古い道床を残します。大きく動かすほど未使用の旧道床が広く残るため、初期試験では小さな移動を推奨します。
- 通常レール・自動分割レールとも、同じ接続端点を持つ2本の同時移動を実機確認済みです。移動後に追加された道床範囲を含む通常の走行も実機で問題がないことを確認済みです。ただし、道床を追加できない交差座標の通過は別途確認が必要です。
- Undoはまだありません。適用前の左クリックによる段階解除のみです。

## builder1実機ログから得た補足

2026-09-02の初回builder1試験では、自由点・既設端点のどちらも最初の道床位置で生成失敗した。原因は`World#setBlock`が`false`を返したこと自体を失敗扱いしていた点で、目的の道床状態が既に成立している場合を区別できていなかった。以後は戻り値ではなく、設置後の`TileEntityLargeRailBase` / `TileEntityLargeRailCore`を再取得して判定する。

またSRB3参照実装との照合により、精密端点、マーカーブロック位置、RTMのYaw規約を別々に扱う必要があることを確認した。通常レール高は1/16ブロック、方向マーカーはブロック中央、既設端部の接続マーカーは隣接ブロック側に置く。Yawは0度が+Z、90度が+Xであり、自由点directionとベジェプレビューも同じ規約を使用する。

## 通常レール再生成テストモデル

`SuperRailBuilderX_RailPositionNormalTest` は、端点の選択と移動先の指定には既存のRailPosition試験ツールをそのまま利用し、適用方式だけを変更する別モデルです。

- 元が通常レールの場合は、既存ツールと同様にRailPositionとRailMapを更新します。
- 元が自動分割レールの場合は、論理RailPosition、RailProperty、信号、サブレールを退避してから論理レール全体を撤去します。
- 移動後は `BlockMarker.createRail` を呼ばず、`RailMapBasic#getRailBlockList` から得た空気位置だけへ道床を配置し、始点ブロックへ単一の `largeRailCore0` を設置します。
- 初回実機試験で、手動宣言型のコアに対する `markDirty()` が1.7.10の実行名へ変換されず、レール生成後に `normal_rebuild_failed` となる問題を確認しました。基本コア型を受け取るcompatヘルパー経由へ統一して修正しています。
- 元のRailPropertyで `autoSplit` が有効でも、この試験経路では分割処理を通らないため、単一コアの通常レールになります。
- 通常レールの生成に失敗した場合は、退避した元のRailPositionからKaizPatchX標準処理で元の自動分割レールを復元します。

このモデルは「自動分割を使用した再生成」と「単一コア通常レールによる再生成」の挙動を比較するためのものです。長距離レールを単一コアにすると、コアのあるチャンクが未ロードのときの挙動など、自動分割で解決された問題が再び現れる可能性があります。必ずバックアップ済みのテストワールドで確認してください。
