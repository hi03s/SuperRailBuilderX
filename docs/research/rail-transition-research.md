# 自由端点とレール遷移の調査

2026-10-12 ローカルCodexによる資料統合。対象はKaizPatchX 1.10.4 / AppleExtended 2.5.3。2026-10-10までの実機観測、公式実装の履歴、対処方式の検討をまとめる。

## 現在の結論

mainは両環境とも完全自由点仕様を使用する。端点をブロック境界へ丸める試作は撤回済み。KaizPatchXと旧AE2.5.3向けのSRBXPatchは車両のレール遷移を補う暫定処理である。AE2.5.4では本体へ取り込まれたため、次回パック更新はパッチなしの構成へ対応する。現行ソースの対応状況と適用範囲は[SRBXPatchの開発資料](../development/srbxpatch.md)を参照する。

`RailPosition#setPosition`で精密な端点を指定できること、幾何学上の端点が一致すること、台車が別レールへ正常に遷移できることは別の条件である。ブロック内部の独立レール接続では、台車の現在RailMapと、予測位置の道床が指す所有コアが食い違う。

- AEでは旧道床の探索が旧mapを選び続け、端部への投影による低速停止や、逆方向での位置飛びが起こった。
- Kaizには端点越えの接続探索があるが、遷移後の床探索で旧コアが再選択され、新旧mapを往復した。
- Kaizの[Issue #534回答](https://github.com/Kai-Z-JP/KaizPatchX/issues/534#issuecomment-6086321090)は、端点をブロック端に置く保証をスクリプト側の責務としている。任意の内部端点接続はSRBXの拡張として支える。AEの仕様判断にこの回答を流用しない。

道床上書きだけが原因とは確認できず、所有先を片方へ付け替えるだけでは双方向走行を保証できない。旧調査での「Mod側の対応が必要」は、任意の精密端点を保つにはJava探索処理への介入が必要という技術上の判断であり、本家の修正義務を意味しない。

## 精密座標と所有情報

| 情報                          | 役割                                           |
| ----------------------------- | ---------------------------------------------- |
| `blockX / blockY / blockZ`    | RailPositionの所有ブロック、探索・保存上の基準 |
| `posX / posY / posZ`          | 曲線の精密な端点座標                           |
| `offsetX / offsetY / offsetZ` | 標準端点と精密端点の差分。NBTへ保存される      |
| 道床TileEntityの所有コア      | その床セルから台車が取得するレールコア         |
| 物理RailMap / 論理グループ    | 自動分割された個々の区間と、元の一本のレール   |

`setPosition`はoffsetを計算して端点を再初期化するが、所有ブロックや道床を自動移設しない。同一性・隣接探索の一部にはブロック座標とdirectionが残る。精密座標の保存は接続先グラフの追加ではなく、幾何的な`canConnect`の成立も床探索で選ばれる保証にはならない。

自動分割コアは同じクラス・メタデータでも、グループUUID、全コア座標、論理端点、担当ratio範囲を持つ。端部の選択は物理コアの種別ではなく論理端点で行い、変更はグループ全体の再構築が必要になる。

Kaizの`findBoundaries`は曲線のチャンク境界交点を求め、`createBoundaryRP`が位置・高さ・接線・カントを保存する。RailMapSectionは元曲線のratio区間へ計算を委譲する。たとえばx=16の境界をz=10.37で横切る曲線は、面中央へ丸めると形状が変わる。この構成と導入コメントから、**ブロック面中央への拘束を緩め、境界上の精密分割点で元曲線を保つ**ことが主目的と推定できる。

任意のブロック内部で独立レール同士を接続する意図、将来の対応予定、AEへの移植経路は差分だけでは確定しない。AEについて任意自由端点の走行を保証する説明は旧調査の一次資料では確認できなかった。

## 実機観測と探索処理

### AE: 低速停止と逆方向の位置飛び

AE 2.5.3の接続点は`(1405.85950, 4.06250, -1600.85950)`。床セル`(1405, 4, -1601)`は接続元コア自身を指していた。

| 観測              | 原因判断に必要な記録                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------ |
| 方向Aの停止       | tick506～538で車体位置が不変。先頭台車は旧コア、index=0/7056、速度約0.028 m/tick、力行P2   |
| 速度を上げて通過  | tick653で速度0.201352 m/tick（20 TPSで約14.50 km/h）、次コアへ切替                         |
| 逆方向Bの先頭台車 | tick390→391で速度0.028520 m/tickは同じだが車体変位約0.21960 m。速度相当との差は約0.19108 m |
| Bの後台車         | 接続切替時、台車位置と接続点上の位置バッファに約0.08744 mの差                              |

実使用の公式JARを`javap`で照合した探索順は次のとおり。

1. `updateBogiePos`が台車位置・速度・movingYawから予測XZを作り、`resetRailObj`へ渡す。
2. `getRailFromCoordinates`が予測XZをfloorした床列を探し、その所有コアを返す。精密端点越えに基づく別map探索はない。
3. 所有コアが変わるとcurrentRailMapを置換し、prevPosIndexをリセットする。
4. 選ばれたmapの最近傍サンプルへ投影する。範囲外では端部へ戻り、超過距離を接続mapへ持ち越さない。

Aでは予測点が旧床セルを出ない間、旧mapの端へ戻る。Bでは精密接続点の手前で次の所有セルへ入り、切替先端部へ早く投影される。速度値一定の変位超過は、通常の加速より位置投影による飛びと整合する。

水平45度の今回の線形では、接続点から次セル境界まで`(1406-1405.85950)×√2 ≈ 0.198697 m`、20 TPSで約14.31 km/hに相当し、通過速度と整合した。これは今回の線形に対する推定であり、曲線・勾配を含む一般的な閾値ではない。

### Kaiz: 遷移後の旧map再選択

実機版はKaizPatchX 1.10.4。型生成基準1.10.3と区別する。初回の接続点は`(-709.85950, 4.06250, 31.85950)`で、床セル`(-710, 4, 31)`は旧コアを指していた。旧物理区間長8.28660 mに対し、新区間は0.19871 mだった。

| 観測               | 原因判断に必要な記録                                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------------------------- |
| 初回の往復         | tick410～496の87 tickすべてで新旧コアが交互に切替。新index5/71から旧終端2983/2983へ戻るなどの反復                     |
| 逆方向の位置飛び   | 約1 km/hで先頭台車切替時の車体変位約0.188196 m。後台車では速度0.015416 m/tick一定で変位約0.106285 m                   |
| 位置変更後         | 新区間長5.85585 mでもtick441～531の91 tickすべてで往復。極短区間は必要条件ではない                                    |
| 往復が止まった時点 | tick532、速度0.102424 m/tickで同じ新mapのindex36→72へ進み、予測床セルの所有先が新コアになった。次区間への到達前に解消 |

実使用JARの探索順はAEと異なる。

1. `findCrossedConnectedCore`で越えた端点の接続コアを優先する。
2. 端点を越えていない場合は予測XZの`getRailFromCoordinates`へ戻る。
3. `keepCurrentSectionCore`は同論理グループ内の保持を行う。今回の旧・新は別論理グループで、この保護対象ではない。
4. 別グループへの切替では`canConnect`を検証し、`findConnectedEntryIndex`で入口を選ぶ。
5. 選ばれたmapへ位置を投影する。旧mapが候補なら旧終端へ戻る。

端点探索で新mapへ入っても、次tickの予測点が旧床セルに残ると旧コアを再選択できる。ログの毎tick往復はこの探索順と整合する。床探索は端部だけの特別処理ではなく、端点越えの優先探索が接続先を返さなかった更新で実行される。台車位置・速度・進行方向による予測と床所有先が関わるため、「短区間を飛び越せば必ず解決する」「AEと同じ必要速度」とは判断しない。

### 観測の限界

旧デバッグ車両の記録はサーバーの移動前callback（`phase=before-movement`）で取得した。速度更新と位置・台車状態に時間差があるため、tickの前後を区別する。Kaizの台車位置/バッファYとmap端点Yには一定差1.1875 mがあったが、AEと直接比較して段差の原因とはしない。

実機ログ・生成時所有情報・実JARの探索順は照合済み。一方、標準マーカー＋offsetによるSRBX非経由の同配置対照、全曲線・全通常レールでの再現は旧調査時点で未実施。初回敷設の所有先変更履歴もなく、過去の上書きがなかったことまで証明しない。

## 対処方式の選択記録

### 採用: 独立したSRBXPatch

既存描画パッチはrendererのScriptEngine内のJavaScript関数を差し替える仕組みであり、台車のprivateメソッドやstaticなJava探索呼出しを置換できない。走行診断のreflection読取りもJavaメソッドの差替えにはならない。このため、既存Mod JARやrtm-tsを編集せず、起動時にJava探索へhookする独立coremodを選んだ。

Kaizは現在mapの保持条件を補い、端点越えをnative探索へ委譲する。AE2.5.3向けパッチは現在mapの保持に加え、自由端点越えの精密接続探索と同グループsection優先を補う。候補の不整合・曖昧さ・未対応状態では標準処理へ戻す。適用範囲と制限は[SRBXPatchの開発資料](../development/srbxpatch.md)を参照する。

### 撤回: ブロック境界へ端点を補正する方式

2026-10-10の試作では、接線が横切るX/Z整数面へ端点を移し、内向き接線側の所有セルとnative directionを合わせた。共有接続は同一座標へ補正し、単一面を共有できない場合はブロック角を使った。曲線分割は元曲線上の境界交点を選び、縦曲線や既設接続との両立が不可能なら破壊前に拒否した。Undoは補正せず保存座標を復元した。

幾何・安全拒否・回帰テストは成功したが、両環境の実機走行で解消したとの確認前に方針を変更した。座標・線形・分割位置を変え、既設内部接続への新設も制限するため、mainの完全自由点仕様には採用しない。境界方式も道床所有競合や重複線路のすべてを解決する保証ではない。

### 採用しなかった案

| 案                                   | 採用しない理由                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------ |
| 毎tick台車のcore/map/indexを強制変更 | native床探索で再選択され、位置・編成距離・同期まで補正が必要                         |
| 通過時だけ道床所有先を変更           | 全車両が共有する状態を変え、逆方向車両・複数列車・Undoと競合                         |
| パックからcontroller/台車を置換      | 既存・保存台車の生成、同期、保存、編成、モデルcallbackを含む汎用処理が成立していない |
| 現在コアを無条件に返す               | 正当な端点越え、別論理グループへの遷移、分岐選択まで止める                           |

## 敷設・移動の安全性に関する知見

遷移パッチとレール再生成の安全性は別に扱う。RailPositionだけを動かして道床を更新しなければ、新しい曲線が旧床範囲を出た位置で`Rail not found`となる。通常・自動分割とも、元のRailProperty・信号・サブレールを退避し、対象全体を撤去して共通生成規則で再構築する。全グループコアのロード・在線・元状態を検証し、失敗時は元状態から復元する。

過去の生成・消失調査で重要な判断は以下。

- `World#setBlock`のfalseは目的状態が既に成立している場合にも返る。戻り値だけで失敗とせず、設置後のTileEntityを再取得して確認する。
- 精密端点、マーカー座標、RTMのYaw規約を分離する。`getNeighborPos`は自由化後の精密端点を使うため、従来の所有ブロック由来の接続座標と一致するとは限らない。
- 既設コアを通常道床へ置換すると、旧コアの破壊処理が論理レールを撤去し、新設ブロックまで消す場合がある。先に空気化する案も交差相手を破壊したため撤回し、既設コア保護を優先する。
- section生成時に共有道床が先行sectionの所有先を保持していると、後段のコア化で自身の論理レールを壊す場合がある。コア化直前に予定位置の所有参照を切り離す必要がある。
- 自動分割区間の端点変更は単体コアの更新では足りない。未初期化コアの無効な論理端点は候補にしない。

旧資料の「Kaiz専用」「途中道床を一律上書き」「セクションコア交差時の単純64 m fallback」は当時の仕様を含む。現行の衝突・端部所有・代替配置規則は[レール生成と自由配置](../development/rail-generation-and-free-positioning.md)を正とする。

## 旧走行デバッグ車両から得た知見

デバッグ車両の登録JSONは除去済みで、現在はモデル選択に出ない。モデル・テクスチャ・診断スクリプトは再利用用に保持する。旧単車は台車間隔2.5 mで、前後運転台と低速ノッチを持ち、通常車両の運動を変更せず内部状態を観測した。

診断は実追従core/map/indexと、床所有先`bed/nearby`を区別する。周辺に道床があることは、そのmapが選ばれた証拠ではない。`index/split`は採用サンプル位置/総分割数で、splitはレール長×360。`possible-stall`は力行中に1tick変位0.0001 m未満が40tick続く条件であり、Kaizの毎tick往復は検知できなかった。これは不具合判定ではなく観測条件である。

旧モデル読込クラッシュはJSONのAlphaBlend/Light省略ではなく、MQOのScene欠落で材質ブロックが読み飛ばされ、defaultテクスチャ参照がnullになったもの。両MQOへSceneを追加して修正した。第三要素の省略はAEローダーで許容される。default追加で材質欠落を隠す方法は採らなかった。

この車両でAE/Kaizの読込・運転・台車診断を確認したが、他車両の台車間隔・編成に固有の問題まで再現する保証はない。現在の確認は通常車両とSRBXPatchの診断を使う。
